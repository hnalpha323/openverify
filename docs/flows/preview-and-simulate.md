# Preview and simulate (plan C156)

## The preview frame (built)

The console shows a flow it is editing in a frame of the flow origin: `<iframe src="{flow origin}/preview" title="Flow preview" sandbox="allow-scripts allow-same-origin" referrerpolicy="no-referrer">`. The flow origin must differ from the console's, or `allow-same-origin` would give the frame the console's own origin. The preview has **no session and no network**: the flow server serves `/preview` with `connect-src 'none'`, the console origin (`OPENVERIFY_DASHBOARD_PUBLIC_URL`) as its only `frame-ancestors`, and no camera ([the flow server](server.md)). It renders what it is posted, with flow-renderer's components, and capture steps as still placeholders; its own chrome is English and says what differs from a live flow (no camera, no checks, simulated outcomes, and the server-side validations it does not run: patterns, field writes, consent digests).

**Protocol** (`packages/contracts/src/flow-messages.ts`, versioned, ours). The console posts `{ source: "openverify-console", version: 1, type, ... }` with the flow origin as `targetOrigin`: `preview-document` (the preview resolve's answer), `select-step`, `set-outcome`, `set-viewport` (320, 375, 768), `set-scheme`, and `preview-assets`. The preview answers `{ source: "openverify-preview", version: 1, type }` (`ready`, `navigated { step-id }`, `error { malformed-document | asset-refused | unknown }`) to the exact console origin, which it reads from a `<meta>` the flow server injects from the same setting as the header. Each side checks `event.origin` and `event.source` (`window.parent`, the frame's `contentWindow`), parses with zod and ignores anything else, a message over 1 MiB included.

**Assets.** The theme's logo and font reach the preview as transferred `ArrayBuffer`s in `preview-assets` (at most two, 1 MiB in all), fetched by the console through `GET /theme-sets/assets/:id/content`; the preview sniffs them again (PNG, JPEG or WebP; WOFF2) before any `blob:` URL or `FontFace`, and its policy is never relaxed for them. The preview applies the theme it is posted, as the live flow applies the session's ([themes](../themes/README.md)).

## The resolve route (C156.1, built in Workflow 9B)

`POST /api/v1/inquiry-template-versions/:id/preview` (`inquiry-templates:read`, API keys and user sessions; the `template-preview` policy, 120 a minute per principal and shared with `simulate` and `validate`, is counted first) answers the document the console posts as `preview-document` (`services/templates/preview.ts`). `meta.locale` is required: a base locale or the pseudo-locales `en-XA` and `ar-XB`. `data.attributes` may carry an unsaved `flow` (v1 or v2), `copy`, `field-schemas`, `theme-set-id` (`null` for none) and `styles`; otherwise the stored version is read. The answer holds every renderable step's client view (a v1 flow is migrated first; branches and actions are left out), the resolved theme with the contrast gate's answer (a failing palette is answered with its findings, not refused), the copy for the locale, and guidance values from configuration only; never inquiry data. Its 422 pointers are `/meta/locale`, `/data/attributes/theme-set-id`, `/data/attributes/styles/...` and `/data/attributes/flow`.

## Simulate (C156.4, built in Workflow 9B)

`POST /api/v1/inquiry-template-versions/:id/simulate` (same scope and policy) walks any version of the caller's environment, a draft included, over a simulated scope (`meta.scope`) or a preset (`meta.preset-id`), exactly one of the two. A flow-spec 1 flow is migrated first, as the engine walks it. The walk uses the engine's own functions (`nextPosition`, `resumeAt`, the server's condition evaluator, core's `decideVerification` over the simulated per-check results, and `flowOutcome`), so it takes the path the engine would take over those facts. The answer, labelled `simulated: true`, lists each step with its port, its route (`key`, `condition-result`, `on-null`, `null-paths`), whether it waited, its notes and every fact a branch read with its tier, stage and source, then the outcome (`status`, `flow-outcome`) and `halted`. Nothing is stored, audited or sent: no run, step record, request or workflow. What each kind of step does in the walk (`services/templates/simulate.ts`):

- a person's step (consent, screen, handoff) is left through `next`;
- a verification step is left through `next` when its simulated status passed, was skipped or is in review, through `exhausted` when it failed and has that edge, and otherwise fails the inquiry there; a verification the scope does not decide stops the path there, pending, as the live flow waits for the person; its facts enter the scope only once the path has entered its step;
- a branch with `waitFor` waits until its deadline: facts the scope leaves unknown stay `null` and follow `onNull` (noted `waited_for_facts`);
- `run_workflow` never runs: it takes the port its simulated status gives, and the path stops there when the scope does not simulate it; `tag_inquiry` changes the simulated tags; `flag_for_review` is noted; `copy_extractions` copies a decided verification's simulated extractions; `update_account_fields` writes nothing.

**A client-unable exit is not simulated** (Phase 10 C207.9). In a live inquiry a client that cannot read a document chip (the web flow always, an Android app without a reader or on a phone without NFC) may leave an `nfc` step through its `exhausted` edge at once, by reporting so; the inquiry then goes to review at completion unless the version carries the acknowledgement `client-unable:<step id>` and the step's `onFallback` is `continue`. The simulated walk takes an `nfc` step's `exhausted` edge only for a simulated failed chip verification, and settles it by `onFallback` as any fallback. So a simulated path through that edge can show `completed` where a client-unable exit of the same version would end in review. Publish warns (`nfc_fallback_missing`) about an `nfc` step with no `exhausted` edge, because every web session and every Android session without a reader stops there.

**Two known differences from a live inquiry** (stated here and in `simulate.ts`; the console labels every simulated path simulated and, since Workflow 9D (K9-8), lists both beside the path): a failure step is shown failed even where Phase 8's decision-record gates would send the inquiry to review at run time (the recorded consent is not simulated); and a simulated `null` signal has no reason, so it never counts in the `needs_review` class of `ON_NULL_DEFAULTS`, while an errored check (`null`) always does.

**Presets** (`GET`, `POST`, `DELETE /api/v1/dashboard/simulation-presets/:id`, `inquiry-templates:read`): the built-in presets come first, `builtin:<type>-passed` and `builtin:<type>-failed` for each verification type with a `null` scope, then the operator's own (`ssp_`, the scope sealed at rest). A preset's scope is served `null` to a reader without `pii:view`; it is still simulated by id. A simulate body's `scope` and a preview body's field defaults are masked in stored API logs.

## In the console (Workflow 9C)

The template's Preview tab (`/templates/[id]/preview`) holds the frame, its controls (step, outcome, viewport, scheme, locale), the banner listing what a preview does not do, and the simulate panel with the presets; the workflow editor's test runs draw on the read-only canvas (`RunOverlay`). The details are in `apps/dashboard/README.md`, "Preview and simulate (C156)".
