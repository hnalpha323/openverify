# OpenVerify — Implementation Plan

> Open-source, self-hostable identity verification platform (Web + Android), feature-modelled on Persona.
> Mode: `/ecc:plan --orchestrate --yes-to-all --run-tdd` · Date: 2026-10-19 · Complexity: **VERY HIGH (multi-run program)**

---

## 1. Requirements restatement

Build **OpenVerify**, a full-featured open-source alternative to Persona (withpersona.com), as one monorepo containing:

1. **Backend platform:** a multi-tenant API covering inquiries, verifications, checks, reports, accounts, cases, workflows, lists, graph, transactions, webhooks, events, API keys/RBAC, sandbox/production environments, and audit logs.
2. **Verification engine:** reimplements Persona's **safety checks** (the 75+ verification checks catalogued in §4) using **permissively-licensed** open models and public data. Where Persona depends on licensed authoritative databases, OpenVerify ships a **pluggable provider adapter plus a deterministic sandbox provider**.
3. **Web:**
   - an end-user verification flow (hosted page, embedded iframe, inline);
   - a JS/React SDK;
   - an operator **dashboard** (review, cases, workflows editor, template builder, graph explorer, settings).
4. **Android:**
   - a native Kotlin SDK covering CameraX document/selfie capture, active liveness, PDF417 and **NFC ePassport/eID chip reading**, and device signals;
   - a demo app.
5. **Engineering bar:**
   - TDD throughout, with ≥80% coverage per package;
   - E2E tests;
   - security review on every security-touching slice;
   - CI;
   - docs.

**Locked decisions (from Q&A on 2026-10-19):**

| Decision | Choice |
|---|---|
| Name | **OpenVerify** (`hnalpha323/openverify`, npm scope `@openverify` is free). Note: `ongov/OpenVerify` exists (Ontario credential app, different domain). |
| Toolchain | Docker Desktop WSL integration **enabled** (verified: Docker 29.7.2). Remaining tools installed userland (no sudo). |
| Stack | **TypeScript** API + Next.js dashboard + TS web SDK · **Python** FastAPI vision/ML service · **Kotlin/Compose** native Android SDK |
| Pre-approved | Accept Android SDK licenses · download permissive models & public sanctions data · create **private** GitHub repo + push · auto-commit per slice (Gate 2) |
| Orchestration | **Medium, phased:** ≤10 agents per Workflow; phases run sequentially, with slices in parallel inside each phase |
| License (default) | **Apache-2.0**. Change before any public release if AGPL is preferred. The NFC module ships as a separate optional artifact under LGPL-3.0, a choice the "or later" grants allow: JMRTD and cert-cvc are `LGPL-2.1-or-later`, and SCUBA is `LGPL-2.1-or-later AND GPL-2.0-only WITH Classpath-exception-2.0` (two Oracle files; `docs/research/phase5-nfc.md` §7.1). |

**Non-goals and legal guardrails:**
- No Persona trademarks, logos, UI copy, or proprietary assets. The README says "inspired by", nominative use only.
- Clean-room: built from public documentation only, with no copied doc text.
- Check identifiers reuse the **descriptive** snake_case names (e.g. `id_glare_detection`) to ease migration. A mapping table is kept in docs.
- No real PII anywhere in the repo:
  - test IDs are **synthetic**, generated by us;
  - test faces come only from **public-domain US-government imagery**, e.g. NASA portraits.
- No model weights with non-commercial licenses (e.g. InsightFace pretrained packs are excluded).

**Data protection by design:**
- PII fields use envelope encryption (AES-256-GCM DEKs wrapped by a KEK read from an environment variable or, in its `_FILE` form, a mounted file, with a previous KEK and `kek:rewrap` for rotation; a KMS adapter is the next release, Phase 11 C249.2, C286).
- Object storage is encrypted.
- Biometric consent screen with explicit opt-in (BIPA / GDPR Art. 9).
- Configurable retention plus scheduled redaction (`*.redacted` events). Biometric data has the shortest default retention.
- PII-scrubbed logs, audit log of every operator read and write, the DSAR access export (a per-account manifest with files, audited, asynchronous and expiring; Phase 11 C253).

**Hardening:**
- CSP and Permissions-Policy (camera) on the flow; `frame-ancestors` is sent per request by the flow server (`apps/flow/server.ts`), never in a `<meta>`, where browsers ignore it (Phase 9 C157).
- Allowed origins for embedding and redirects per environment, narrowed per template; `localhost` embedding is allowed in sandbox only; the flow server fails closed to `frame-ancestors 'none'`.
- SSRF guard on the HTTPS-request workflow action (blocks private ranges, DNS-rebinding defence).
- Argon2id passwords, TOTP + WebAuthn MFA; console sessions with a 30-minute idle timeout beside the 12-hour lifetime, a login limiter in Valkey that fails closed, and OIDC sign-in (Phase 11 C245, C246, C248).
- Scoped, hashed API keys with pepper rotation (C247).
- HSTS at the ingress, set by the chart (one year, subdomains, no preload), with an optional header in the apps for installs without such an ingress (C255.1).
- The internal listener (`OPENVERIFY_INTERNAL_LISTEN`): internal routes on their own port, with the ingress's deny as a second layer (C250.3).
- Per-tenant queue quotas: per-environment in-flight caps for the queues that hold tenant work (C251).
- Two database roles: a migration role that owns DDL and a runtime role that cannot create objects, with a locked `db:migrate` (C249.3, C249.4).

## 4. Safety-check catalog: Persona check → OpenVerify implementation

Tier key:
- **R** = real implementation, deterministic or with an open model.
- **H** = heuristic, shipped as `beta` with a confidence score.
- **A** = provider adapter plus a sandbox provider (needs licensed data or a key).

Type key: UB = user behavior, F = fraud.

### 4.1 Government ID (`verification/government-id`)

| Check | T | Type | OpenVerify approach |
|---|---|---|---|
| id_unprocessable_submission_detection | R | UB | Quad detection + OCR text density + portrait presence ⇒ "not an ID / unreadable" |

| id_glare_detection | R | UB | Specular-highlight ratio over text and portrait ROIs |

## 7. Orchestration and TDD protocol (`--orchestrate --yes-to-all --run-tdd`)

- **Gate 1 (plan):** approving *this* master plan approves the phase task lists derived from it. Each phase writes `docs/plans/phase-N.plan.md` before coding.
- **Gate 2 (commit):** pre-approved. The main session commits only after tests, coverage and review pass. Commits:
  - are conventional (`test:` RED → `feat:` GREEN → `refactor:`);
  - end with `Claude-Session: https://claude.ai/code/session_01RVjoMfVmvhCPn3vsCzYr8A`.
  - Push goes to the private repo. Never force-push.
- **Per-phase Workflow (≤10 agents):**
  - slice implementers run in parallel, each in an isolated worktree, following `tdd-workflow`: RED evidence, then GREEN, then refactor, then an evidence report in `docs/tdd/<slice>.tdd.md`;
  - an integration agent merges and runs the full suites;
  - review: code-reviewer + the language reviewer + security-reviewer, with adversarial verification of CRITICAL/HIGH findings;
  - a fixer agent handles the remaining findings;
  - the main session re-verifies and commits.
- **Coverage gates:** Vitest thresholds 80% per package; `pytest --cov-fail-under=80`; Kover 80% (logic modules).
- **Security records at each phase:** every phase plan has a "threat-model rows added or changed" line, and the threat model (`docs/security/threat-model.md`) and the ASVS and MASVS checklists are reviewed at each phase end, the review's commit recorded in `docs/PROGRESS.md` (Phase 11 C273.5, C274.6; ADR 0010 rule 6).
- **Stop/skip rule:** if a slice fails 3 fix attempts, it is logged as a blocker in `docs/PROGRESS.md` and the run moves to the next independent slice. No destructive operations outside the repo. Secrets never get committed (gitleaks).
- **Morning report:** `docs/PROGRESS.md` holds per-phase status, test/coverage numbers, blockers, and what's next.
