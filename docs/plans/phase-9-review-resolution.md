# Phase 9 plan: resolution of the first review round

Three adversarial reviews read the first draft of `phase-9.plan.md` on 2026-10-29: privacy, security and law (P01–P37), honesty and product coverage (H01–H30), and feasibility and fit with the code (F01–F29). Together they raised 4 CRITICAL, 20 HIGH, 50 MEDIUM and 22 LOW findings, 96 in all. The honesty review's own summary says "31 findings" and "7 LOW", but it lists H01–H30, of which six (H25–H30) are LOW; this resolution counts what is listed.

Every finding was checked against the repository at `42895e6a` (read-only) and against the Phase 7 and Phase 8 plans that Phase 9 builds on. "→" names where the revised plan carries the fix, by contract item, Workflow or decision number. Where a reviewer offered alternatives, the one taken is named with its reason. Findings raised by more than one lens are resolved once, under the first lens that raised them, and the others point there.

Checks made for this resolution (beyond the reviewers' own evidence):
- `FlowCoordinator.kt:432-438` (`sendConsent` copies the consent into the cached session and walks on without a refetch), `:487-527` (`resolve` walks with the navigator built in `adopt`, `:1228`) and `FlowNavigator.kt:26-36` (list order when no transition matches): H01 and F01 hold as stated. `Flow.kt:444-457` decodes any unknown `type` as `UnsupportedStep(id, type)`, so a placeholder step of an unknown type is a safe stop.
- `docs/plans/phase-7.plan.md:239` (C90.5: signals are computed on the inquiry's first move into `completed`, `failed` or `expired`) and `:933` (C99.4: list screening starts at the first move out of `pending`): H02 holds, and the same timing means that no list screening finishes before completion either, which the plan's `lists.*` rule already allows for.
- `git grep -E 'ov_(sbx|prod)_[A-Za-z0-9_-]{43}'` finds 10 tracked tokens in 8 files (F02). The wider rule P33 asks for also matches tracked tokens with no "synthetic" in them (`ovo_ooo…`, `ovs_ttt…` in Android tests and `docs/tdd/kmp-foundation.tdd.md`), and the CI scan reads the whole history, so the allowlist also needs an entropy floor (P33, F02).
- `packages/ui/src/button.tsx:18`: the danger button renders `text-on-primary` on `bg-danger`, so the theme's `on-danger` token has no consumer (F13).
- `packages/db/src/tables/users.ts:81-117`: `user_sessions` records `mfa_satisfied` (a boolean) and no time of verification, so P02's step-up needs a new column.
- `packages/db/src/tables/inquiry-templates.ts:68`: `published_at` exists on versions (H23's `published-at`).

### Owner questions still open

Every plan decision (1–73) still reads "confirm or change", and decisions 67–73 from the first round are still open with their defaults. This round adds or reshapes the following; each default is what the build uses until the owner answers, so none blocks 9A.

1. **Deactivation without a second factor** (V05, decision 70). Default: an actor with no enrolled factor may deactivate (never reset or reactivate) a user they out-rank; an actor with a factor must step up. Alternative: step-up for every action on another user, which blocks deactivation in organisations without `require-mfa`.
2. **Analytics freshness against differencing** (P21, decision 72). Default: outcome figures of the last 30 days (open days) refresh once a local day, while `created` and `started` refresh every 5 minutes; a once-a-day difference stays a stated limit. Alternative: 5-minute outcome figures with snapshot differencing stated as an unmitigated limit.
3. **The settle window without a retention bound** (H04, decision 72). Default: 30 days (1–90), with redaction recording each inquiry's counts before clearing it. Alternative: keep a retention bound, which cannot hold against on-demand redaction or per-version retention.
4. **Custom consent copy and today's Android SDK** (V11). Default: a version with custom consent copy serves its consent step as unsupported to spec-1 clients, so today's Android SDK cannot run it until Phase 10; publish warns. Alternative: none that keeps the consent record honest.
5. **Pattern features** (V10). Default: no case-insensitive (`i`) matching and no `\p{…}` classes in field patterns. Alternative: source Unicode case-folding and property tables (generated at build time from the runtime) in a later phase.
6. **An early-signal null reason** (V06, decision 68). Default: `not_yet_collected` in Phase 7's `ignore` class, a labelled amendment, so an early signal branch follows its own `onNull`. Alternative: a publish rule that forbids client-collected signal branches before a screen after consent.
7. **The internal route in production** (V13, P31). Default: Phase 11 denies `/api/v1/internal/*` at the chart's ingress (or binds it to `OPENVERIFY_INTERNAL_LISTEN`); until then the flow-server token protects it. To be settled in Phase 11's plan.
8. **How the flow server loads shared code** (V04). Default: one import-free module behind a source-condition subpath, run with `node --conditions=@openverify/source`; fallback `dist` with a build dependency if Node refuses the workspace link. Technical, recorded for visibility rather than as an owner choice.
