## Slice 12: JIT in the re-screen's own reads (item 5): none at scale, so no setting

Decision 4 asks for `SET LOCAL jit = off` in the re-screen's reads only where `EXPLAIN (ANALYZE)` at scale shows JIT time, as `retrieveCandidates` showed it (up to 680 ms a statement at 2,000,000 names). PostgreSQL 17 plans JIT only above `jit_above_cost` (100,000, the image's default; `show jit` is `on`). Every read the re-screen makes was explained on the development tables (my seed, 100,000 names, 200,000 recurring subjects; database `evaluation-6-100k-rs6d-head-prof`) and, for the two reads whose cost grows with the list, on the 2,000,000-name table (412,582 entries, eight syncs of about 51,600 changed entries each, `watchlist_key_df` 872,899 rows, so the re-screen reads it key by key), each under the e2e lock:

|---|---|---:|---:|---|
| `listRecurringReportSubjects`, a chunk of 50,000 | 100,000 names | 12,116 | 447 ms | none |
| `listRescreenEnvironments` | 100,000 names | 17,060 | 461 ms | none |
| `watchlistKeyFrequencyTable` (count, then the whole table) | 100,000 names | 1,979 and 1,770 | 107 and 15 ms | none |
| `listChangedWatchlistEntries`, the first page of the 60,565-entry import | 100,000 names | 16,843 | 247 ms | none |

`listReportsWithLiveMatches` and `insertListUpdateRuns` take 500 ids a statement by primary key and index. No plan crosses the JIT threshold and no output has a `JIT:` block, so neither `report-rescreen.ts` nor `listChangedWatchlistEntries` gets the setting: a setting no measurement asks for would be a change without a test of its effect. The changed-entry page on the 2,000,000-name table is the nearest (81,208): a sync of about 65,000 changed entries would cross the threshold.
