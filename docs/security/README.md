# Security records

OpenVerify's security documents (PLAN §10; Phase 11, C273 to C276). Each describes the code at its commit and has a test that fails when it drifts from what the repository holds, where a machine can compare; a review reads the rest at each phase end. They are the project's own assessment: nothing here is a certification, an audit or an attestation by a third party.

## The wording rule (C274.5)

The threat model and the checklists are self-assessed. No document calls OpenVerify, an install or a checklist row certified, and no document says that anything complies with or is compliant with ASVS, MASVS or a law; a status is set from evidence at a commit, never from a target. A word of that kind may appear only in a sentence that denies it, or quoted on its own as a word. The wording test of `packages/docs-tools/src/wording.ts` holds every page of `docs/`, every `README.md`, `SECURITY.md` and the chart's description to this rule.

## How the records stay current

- Re-render the generated pages: `pnpm --filter @openverify/docs-tools docs:all`; check every record: `pnpm --filter @openverify/docs-tools test`.
- A new sealed column, secret variable, redaction path, HMAC label or token prefix fails a record test until its page names it; a new document in this folder fails the index's test until it is linked above.
- The threat model and the checklists are re-reviewed at each phase end, with the review's commit recorded in their rows.
