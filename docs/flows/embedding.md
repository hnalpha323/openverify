# Embedding and redirects (plan C158)

## Allowed origins

`allowed-embed-origins` is an environment setting (`settings:write`, audit-logged, at most 50). Each entry is `https://host[:port]` or `https://*.host[:port]` (a CSP host-source): no path, query, fragment, userinfo, IP literal, bare `*` or `*` port; IDNs as `xn--`, lower case. Production refuses `http:` and `localhost`; a sandbox also takes `http://localhost[:port]` and `http://127.0.0.1[:port]` (`https://127.0.0.1` is refused as an IP literal). A wildcard needs at least two labels after `*.`, is refused on our list of shared-hosting suffixes (`SHARED_HOSTING_SUFFIXES`, incomplete by design: the Public Suffix List is MPL-2.0 and cannot run in the API), and in production needs `meta.acknowledge-wildcards: true` on the change (otherwise 422 `embed_wildcard_unacknowledged`). Invalid entries answer 422 `embed_origin_invalid`, each named by its pointer. Our setting holds origins, so scheme and port are explicit, where the public product's allowlist holds bare domains.

**One matcher.** `matchesOriginPattern(origin, entry)` in `@openverify/contracts/origin-pattern` (a module with no import at all, golden vectors in `contracts/fixtures/origin-pattern/vectors.json`) implements CSP host-source matching (the scheme, a dot boundary at any depth, the scheme's default port), so `https://evilhost.com` never matches `https://*.host.com`. The settings, the flow server and the embed bridge all use it.

## Rules

- A version's `embed-origins` narrow the environment's list for its inquiries (empty or absent: the environment's list). The served `frame-ancestors` is always within the environment's list, whatever the version stored. At publish (and in `validate`'s publish mode) each entry of a version's list must be in the grammar and on the environment's list, else 422 `embed_origin_invalid` at `/data/attributes/embed-origins/<i>` ([settings: origins](../settings/origins.md)).
- An inquiry embeds only while its template is active; an unknown inquiry and an inactive template get the same answer (`'none'`). Drafts never embed: inquiries pin published versions, and the preview is the only draft surface.
- The embed bridge checks that the path's inquiry id equals the session's own inquiry, the server's truth rather than the fragment's, and otherwise shows its link error.
- CORS is unchanged: the embedded flow is served from the flow origin and calls the API as the hosted flow does.

**What an allowlist does not stop** (ADR 0008): a compromised allowed site, a top-level copy of the hosted page on a phishing domain, or a browser that ignores CSP. `frame-ancestors` in a `<meta>` is ignored by browsers and the header overrides `X-Frame-Options`, so the header the flow server computes is the only control; a static host cannot embed.

## Redirects (C158.4, C158.5)

`redirect-uri` on `POST /inquiries` (public) is checked against the environment's `allowed-redirect-origins` (default: the embed origins), with the same grammar and production rules: an entry without a wildcard matches by parsed scheme, host and port exactly; a wildcard through `matchesOriginPattern`; a custom scheme only when the version lists it in `redirect-uri-schemes` (`^[a-z][a-z0-9+.-]*$`; `javascript`, `data`, `vbscript`, `file`, `blob`, `about`, `filesystem`, `intent`, `http` and `https` refused); userinfo refused; 422 `redirect_uri_not_allowed`. A template version's own `redirect-uri` and `redirect-uri-schemes` are stored as sent with a draft and checked at publish by the same rules (422 `redirect_uri_not_allowed` at `/data/attributes/redirect-uri` or `/data/attributes/redirect-uri-schemes/<i>`); every redirect, either kind, is checked again against the current lists on every session answer, so nothing outside them is ever served, and removing an origin also stops redirects for inquiries already created (the flow then shows its final screen and does not navigate).

On completion or failure the session's `completion.redirect-url` is the URI with only `inquiry-id` appended, plus `status` when the version sets `redirect-include-status: true` (default `false`, because "this inquiry failed" in a landing page's query reaches its logs, analytics and later referrers). The public product also appends a reference id and fields; we do not, to keep personal data out of URLs. **`status` is a hint, not authoritative**: read the inquiry or the webhook. The flow announces the outcome in a live region and shows a "Continue" button that performs the redirect; it never navigates on a timer (WCAG 2.2.1).
