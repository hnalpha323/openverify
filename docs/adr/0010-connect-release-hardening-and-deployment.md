# ADR 0010: Connect, release hardening and deployment

- **Status:** Accepted. Its Connect half, rules 1 to 3, was written in Workflow 11A Stage 1a (2026-11-11); its deployment half, rules 4, 4a and 5, in Workflow 11C Stage 1a (`contracts-11c`, 2026-11-14); rule 6 and this final form by `integration-11e` in Workflow 11E (2026-11-20; Phase 11 decision 46, C282). The six rules are the plan's Summary's.
- **Date:** 2026-11-11
- **Related:** ADR 0002 (check tiers and honesty), ADR 0005 (report honesty), ADR 0007 (workflows), ADR 0008 (flows decided on the server), ADR 0009 (the Android SDK); `docs/plans/phase-11.plan.md` C230–C244, C256 and decisions 17–29, 35, 36, 71, 76 and 77, for the deployment half C257–C267, C289 and decisions 2–6, 42–44, 49–53, 59 and 73–74 (with its "Workflow 11C Stage 1a amendments"); and for rule 6 C273–C275, C284 and decision 7 (with the "Workflow 11E Stage 1a amendments"); `docs/plans/phase-11-review-resolution.md`; `docs/research/phase11-connect.md` and `phase11-inventory.md`.

## Context

Until Phase 11 an organisation that verified a person could not share that result with a partner, and the consent it recorded named no recipient, no purpose and no text. Connect adds sharing between organisations. Three things make it risky:

1. **It is the first path between tenants.** Every other read and write in the platform is scoped to one environment. A sharing feature that reached across tenants in more than one place would be hard to review and easy to widen by mistake.
2. **The data is someone else's.** The person whose identity documents, face and check results are shared is not a party to the agreement between the two organisations. Their consent has to be specific: to whom, for what, which categories, under which words.
3. **A copy looks like a result.** A verification the source ran last year, copied into the destination, has a status of `passed`. If the destination's decision rules, workflows or pass rates read it as a check the destination ran, the platform would be faking a pass (`CLAUDE.md` rule 5).

## Decision

### 1. One install, one witness

Sharing moves data between two organisations of **one install**, on the server. The install's operator is the trust anchor both sides rely on: it sees both tenants, witnesses the consent in a flow, and enforces the share policy. The documentation says so. Sharing between two installs needs a key exchange, a trust bootstrap and a signed envelope, and waits for a later release (C286).

What follows from it:

- Connect is off unless the install sets `OPENVERIFY_CONNECT_ENABLED`, and an organisation receives connections only after its admin turns on the organisation setting `connect-inbound`. While the switch is off every Connect route answers the generic 404 and a `share_consent` step fails publish.
- A connection goes from a source organisation to a destination and carries a **versioned share policy**: the source types, the verification types, the field allowlists, whether files and biometric data may move, what a peek shows, and which shares an attested consent may authorise. The destination accepts a stated version in the console, with a second factor, and cites its data-sharing agreement. A policy change returns the connection to `pending`.
- **One cross-tenant path.** Every read and write of another environment's rows goes through `apps/api/src/services/connect/cross-tenant.ts`, which takes a token or connection already bound to the caller. Each Connect repository keeps its cross-environment functions in a separate `*.cross-env.ts` module, and an import rule with a source test lets only that one file import them.
- **One 404.** A token, connection or consent record the caller may not see answers one body, built by one function, byte-identical whether the object is unknown, another organisation's, or the other environment kind's.
- A share token is a **handle, not a secret**: a ULID that is logged and never hashed. Every call is authenticated and bound to the token's connection, the caller's organisation and side, and the environment kind (sandbox only to sandbox, production only to production). No token id, connection id or source object id appears in any URL the person sees, in any client view or in any Android entry point.
- In the counterparty's audit entries the actor is only `{organization-id, kind}`: one controller's staff are not disclosed to the other.

### 2. No share without a recorded consent

Every share token cites a **consent record of the source environment** that names its recipient, its purpose and its data categories, and that has not been withdrawn, has not expired and has not been cited by another token. A redemption cites a consent record of the destination environment in the same way.

- A record made in a flow (`method: flow`) holds the SHA-256 of the exact text the server composed and served (placeholders filled, NFC), with a sealed copy of that text. It is **witnessed** only in what the platform saw: the server served the text, the client reported showing it, and an affirmative act happened in a session. It does not prove who held the device or that the text was read.
- A record an operator attests (`method: attested`) holds the operator's own text, an evidence reference and a time. It is labelled **not witnessed** in the API (`witnessed: false`) and in both consoles, and the destination sees that label on the token. Attesting needs its own scope, which no key holds by default, and a share that carries biometric data rests on an attestation only where the destination accepted that in the policy.
- A share that carries biometric data needs a separate, explicit, unticked tick with its own text and digest. Face templates are never shareable, whatever the policy says.
- **A decline is a record.** Declining never ends the flow. It writes a `declined` record that no token or redemption can cite, and that blocks an attestation or an API redemption that would override it.
- **Withdrawal** stops every future transfer under the record: an unredeemed token expires, a pending redemption fails at commit, and for a redeemed share the counterparty receives an event so that its operator can act. A copy already made belongs to its controller; the platform cannot recall it and the documentation says so.
- The built-in consent texts are legal texts. The English text is the source, the other four locales are machine-drafted, and all of them are marked "not reviewed by counsel" until the owner records counsel's review (Q7). Publishing a template that uses them needs an audited acknowledgement.

### 3. A copy is never a fresh pass

A cloned verification keeps its source's status, checks, tiers and stages. Every cloned inquiry, verification, check and file carries `provenance` (`kind: connect-clone`, the share token, the source organisation's name, the source's status and times) and `cloned: true`. A hydrated object carries `kind: connect-hydrate` with the keys that were filled. The source's object ids are not disclosed.

- **Off by default.** A cloned inquiry is created in `needs_review`, whatever the source's status. A cloned verification counts toward no required check: in a flow the step runs as if no copy existed.
- **Opt-in per template version.** The setting `accept-cloned-results` lists verification types and a maximum age. Publishing it needs the audited acknowledgement `cloned-results`. With it on, a cloned **pass** of a listed type, younger than the maximum age at the destination's decision, counts toward that step. A cloned **failure** never declines or fails anything by itself: it sends the inquiry to review. The decision record names the share token and says it relied on a cloned result.
- **The person is bound to the copy.** A template that reuses cloned results in a flow keeps a live selfie matched against the cloned portrait, or carries the separate audited acknowledgement `cloned-results-unbound`.
- **Outside the decision engine too.** Cloned rows stage no `verification.*` event and no check-level event. Every `inquiry.*` event about a cloned inquiry carries `provenance`. A workflow condition treats a cloned check as absent unless the rule above counts it. Analytics exclude cloned checks and verifications from pass rates and failure distributions.
- **A copy is never passed on.** A source that is a clone, or holds one, is refused at token creation and again at redemption (`source_is_copy`).
- The flow never shows a hydrated or cloned value to the person, so whoever opens a forwarded link learns nothing from the copy.
- The console never shows a cloned result without its marker.

### 4. Nothing published without the owner

The release workflow builds, scans and stages every artifact; it publishes none of them until the owner has decided where and as whom (Q1 to Q4, C262, C285, C289):

- **What is staged.** `.github/workflows/release.yml` (dispatched by hand on `main`, read-only token, every action pinned by commit) builds the five production images for `linux/amd64`, the chart package and the npm tarballs of `@openverify/js`, `@openverify/node` and `@openverify/react`; scans each image and SBOM; installs and upgrades the chart on kind; runs gitleaks over every unpacked artifact; and uploads everything, with its SHA-256, as workflow artifacts for 30 days. `android-release.yml` stages the Android repository the same way, with each AAR's SBOM.
- **The switch.** The `publish` job runs only inside the GitHub environment `release` (deployment branch `main`, the owner's reviewer where the plan allows one) and only when the repository variable `OPENVERIFY_PUBLISH` is `'true'`. Until the owner sets both, a run ends after staging.
- **What waits for the owner, and why.** Q1, the repository's visibility: keyless signing writes the repository's identity to Sigstore's public log, and artifact attestations and environments on a private repository need paid plans. Q2, the registry and the images and chart it holds. Q3, the signing identity. Q4, the `@openverify` npm scope. The owner granted all four on 2026-11-21 (the orchestrator under the owner's delegation): the repository stays private until the release and is made public at the owner's release step; GHCR under the owner's account, images by digest and the chart as an OCI artifact; cosign keyless with GitHub's build-provenance attestations; the three npm packages with provenance once public. Granting them wires the publish job; it publishes nothing by itself, and nothing is signed, attested or pushed until the owner's release step (the public repository, the `release` environment with its reviewer, `OPENVERIFY_PUBLISH` set to `'true'`) and an approved dispatch with the `dry-run` input set to false; until then the release notes give each artifact's SHA-256 (C262.4).
- **Owner-dependent artifacts are labelled, not hidden.** A shipped component whose licence row still waits for the owner (nodemailer's MIT-0 until Q11 was granted on 2026-11-21; since then FFmpeg, libquadmath and libgfortran inside the vision image's OpenCV wheel, KP11-39) is reported by the licence check as `owner`, and its artifact is staged as `pending-owner`, in its name and in the release notes; staging and the default `release:check` do not stop for it, and `release:check --tag` refuses the tag until it is decided or its decline outcome is built (C261.2, C284.2).
- **Decline outcomes are built, not promised.** Each owner item has an outcome the release ships if the owner declines (C289). The flow image is staged twice: with on-device face guidance (`onnxruntime-web`, whose WASM carries Eigen under the narrow Phase 10 P2 grant) and as `openverify/flow:<version>-noguidance`, built with `OPENVERIFY_FLOW_FACE_GUIDANCE=off`, the image the release ships if that grant is withdrawn. Install switches stay off in every image and chart default while they wait for the owner: `OPENVERIFY_CONNECT_ENABLED` (decision 71). `OPENVERIFY_WATCHLIST_UN_OPT_IN_ALLOWED` waited the same way until Q10's grant (2026-11-21, on ADR 0005's reading); it is now true in the documented defaults (`config.ts`, `.env.example`, compose, the chart), no image bakes it, no seed opts an environment in, and each environment screens `un-sc` only after its admin's audited acknowledgement of the UN's terms.

### 4a. Production images and the chart

The production deployment is five images, one per process, and one Helm chart over the operator's own data stores (C257, C263, C264):

- **Images.** `openverify/api` (the server, the worker, its health probe and every operator command, compiled; no `tsx`, `vitest`, `typescript` or other development tool), `openverify/dashboard` (Next.js standalone output with the console's custom server), `openverify/flow` (the flow server and the built bundle, reading the API's origin at start, so one digest serves any install), `openverify/vision` (model weights never inside; they come from a volume) and `openverify/code-runner`. Each is multi-stage, runs as uid and gid `10001`, works with a read-only root filesystem and a writable `/tmp` only, carries no `HEALTHCHECK` (the chart's probes decide) and no secret in a layer, a label or a build argument, and is built on a base image pinned by digest. Published images would redistribute their base distribution's packages, some under the GPL, as aggregation beside our code; the release notes point at each base's source archive.
- **The chart.** `deploy/helm/openverify/` runs every pod under the restricted Pod Security Standard (non-root, no privilege escalation, every capability dropped, `RuntimeDefault` seccomp, a read-only root with an `emptyDir` `/tmp`, no service-account token), behind default-deny network policies both ways: vision and the code runner have no egress at all, the data stores are reachable only from the processes that use them, and the public internet only from the API and the worker, minus the private, link-local, CGNAT and metadata ranges. The chart creates no Secret; each process reads only its own Secret, mounted as files at mode 0440 and read through the `_FILE` form of each variable. Model weights are fetched by a separate hook Job into a volume vision mounts read-only. HSTS and the request body limits are set at the ingress, which never routes the internal listener. No subchart and no Bitnami image are used.
- **SBOMs and their licence check.** Syft writes an SBOM of each image, of the source trees and of each npm tarball, and the CycloneDX Gradle plugin one per published Android module; `security/check-sbom-licences.py` checks every shipped component against rule 4's list, the recorded owner exceptions only in the artifact they name, and the hand-listed vendored code (Eigen, SCUBA's two files) that no tool resolves. An SBOM lists what its tool resolved; what it cannot see is listed by hand.
- **What these defaults do not guarantee.** Network policies do nothing without a network plugin that enforces them; TLS to the stores, the secret store, backups and log shipping are the operator's. A kind install proves the chart renders and starts, not its behaviour under a real cloud.

### 5. Tools follow rule 4

Every scanner, SBOM tool, chart tool and load tester is permissive, pinned and checksummed, and is installed by our own script or lockfile, never through a mutable third-party action (C258):

- **Why.** On 2026-03-19 a compromised Trivy release was published and 76 of 77 tags of `aquasecurity/trivy-action` were force-pushed to credential-stealing code (CVE-2026-33634). Users who referenced images by digest, or who built from source, were not affected. A scanner runs with the repository checked out, so a scanner is part of the supply chain it checks.
- **Binaries by checksum.** Each tool that ships a release binary (Trivy, osv-scanner, Grype, Syft, zizmor, cosign, Helm 4.3.1 and 3.22.1, helm-unittest, kubeconform, chart-testing, kind, kubectl, gitleaks) is installed only by its `infra/scripts/install-<tool>.sh`: linux x86_64 only, the version and its SHA-256 pinned in the repository and checked against the release's own checksum file, in a private temporary directory. Where the project signs its release, the signature is verified with cosign for the exact workflow identity, and cosign itself is checked by SHA-256 only. Never `curl | sh`, `go install`, a package manager's unpinned copy or `latest`.
- **Packages by lockfile.** pip-audit, which publishes no binary, runs from its own uv project (`security/pip-audit/`) with a hashed lockfile; `eslint-plugin-security` is a root dev dependency in `pnpm-lock.yaml`; the CycloneDX Gradle plugin is held by `android/gradle/verification-metadata.xml`, written from an empty Gradle home. Every transitive licence is recorded before adoption; a plugin's dependency under a licence rule 4 does not list is kept off the classpath or the plugin is not adopted.
- **Images by digest.** Every image a Dockerfile, the compose file, the e2e driver, a test or the chart names carries `tag@sha256:<digest>`, and Trivy's checks bundle (policy, not vulnerability data) is pinned by digest too. Vulnerability databases are the opposite: fetched fresh on every run, or refused when their build date is older than 24 hours, so a clean scan never rests on a weeks-old view.
- **The release age.** Every pin was at least 14 days old on the day it was adopted, with its date recorded in `THIRD_PARTY_LICENSES.md`. The owner's rule (Q5, granted 2026-11-21) is that the 14 days cover toolchain binaries, base images and Actions as they cover packages; so uv 0.13.3 was replaced by 0.13.7, the newest uv at least 14 days old on that day, in CI's three `setup-uv` steps (with the asset's recorded SHA-256 as `checksum`) and the vision image's build stage, and every `uv.lock` was re-checked under it with no version moved.
- **Copyleft tooling stays out.** A tool or ruleset under the GPL, AGPL or LGPL never runs, even as tooling: no Semgrep engine or registry rules, no Opengrep, and no `ct lint`, because it runs yamllint (GPL-3.0); chart lint is `helm lint` and kubeconform, and `ct` is used for `install` only.
- **One gate with expiring exceptions.** The per-push supply-chain job fails on every critical or high finding, with or without a fix, unless `security/allowlist.yaml` names it with its reason, an expiry at most 90 days ahead and who added it; an expired entry fails the job. A pin and a checksum prove that the bytes are the ones reviewed, not that the reviewed release was benign, and a clean scan means the scanners found no known, published weakness in what they could see, not that the code was reviewed.

### 6. Self-assessed, never certified

The threat model and the two checklists are the project's own assessment of its own code, written and reviewed by the agents that build it. No auditor, laboratory or certifying body has read them, and no certification or conformance is claimed for ASVS, MASVS or anything else (C273, C274, C275; decision 7):

- **What exists.** `docs/security/threat-model.md` (STRIDE over the trust boundaries B1 to B14 and the cross-cutting BX, with a Mermaid data-flow diagram per boundary group; every row `control`, `operator`, `accepted` or `gap`); `docs/security/asvs-5.0.0-l2.csv` (one row per ASVS 5.0.0 requirement at levels 1 and 2) and `docs/security/masvs-2.1.0.csv` (one row per MASVS v2.1.0 control, for `openverify-sdk`, `openverify-nfc` and `openverify-face`; the demo app is not shipped), with the generated `docs/security/asvs-summary.md`. Only the standards' requirement ids are committed (`asvs-5.0.0-l2-ids.txt`, `masvs-2.1.0-ids.txt`, written by `scripts/fetch_asvs.py` and `scripts/fetch_masvs.py` from pinned exports): both texts are CC BY-SA, so no requirement's text is copied.
- **Status from evidence, never from a target** (review H15). A row is `met` only when the code at its reviewed commit does it on every supported install path, compose and the chart, and it cites a test or check that ran locally at that commit, never a CI job alone (11E decisions item 6; no CI run is counted on while the owner has no Actions minutes). Otherwise it is `partial` with the missing path named, `gap` with the phase, release or finding id that closes it, `operator` when only the install's operator can meet it (the self-hosting guide's hardening checklist lists those), or `not_applicable` with its reason.
- **Tested, so the records cannot drift silently.** `packages/docs-tools` parses the threat model (every boundary covers all six STRIDE letters or says why a letter does not apply, every `control` cites paths that exist, every `gap` names its owner, every accepted risk names its monitoring) and holds each checklist to exactly its id list, with existing evidence paths and a test among a `met` row's evidence; a wording test fails "certified", "compliant" and their kin next to ASVS or MASVS, unless the sentence denies them; metric names come only from `apps/api/src/metrics-registry.ts`. A row whose cited files changed after its `reviewed_commit` is reported by `pnpm release:check` as an owner item, and `--tag` refuses it (C274.6).
- **Reviewed at every phase end.** The review is recorded with its commit: in Workflow 11E, `docs-security` reviewed the threat model and both checklists against the tree at `7d813b436` (2026-11-20, `fc8cb31ee`), and `integration-11e` confirmed it against the Workflow's final tree. Every later phase plan carries a "threat-model rows added or changed" line, and the threat model and the checklists are reviewed again at that phase's end (PLAN section 7).
- **What it does not say.** A `met` row means the cited evidence exists and agrees with the requirement as the project reads it; it does not mean an independent tester found nothing. The project's own scanners, the DAST scan of Workflow 11F and the review of each phase lower the odds of an unknown weakness; they do not prove its absence.

## Consequences

- Two organisations that do not share an install cannot use Connect in this release.
- A destination that turns `accept-cloned-results` on relies on another organisation's checks and configuration. The platform makes that visible and recorded; whether it is acceptable is the destination's business and legal decision.
- Scopes, limits and the share policy bound what the platform copies. They cannot stop a recipient from misusing data it was entitled to receive, and the policy says nothing about what the destination does with a copy.
- Every constant of Connect is provisional, with its basis stated where it is defined: ten peeks per token, 60 redemptions and 60 peeks a minute, 50 verifications, 200 files and 512 MiB per redemption.
- Backups keep redacted data until they expire, and the platform cannot reach a copy outside itself.
- Nothing of this release is published, signed or attested until the owner answers Q1 to Q4: operators build the images and the chart from the repository, or take the staged artifacts with their SHA-256, and verify those digests themselves.
- A pinned, checksummed tool is the release that was reviewed, not a proven-benign one, and a clean scan covers only what the scanners can see; the remaining risk is stated in the threat model's supply-chain rows (boundary B14).
- The security records are only as current as their last review. Between phase ends they can lag the code; the staleness check names the rows whose evidence moved, and the owner's review of the release checklist is the gate.

## Alternatives not taken

- **A token that is a bearer secret.** Rejected: a secret in a URL or a log is a share. A handle that is useless without the recipient's own credentials is not.
- **A prefetched copy when a token is created** (the public API's `ready` state). Rejected: it is a cached copy of personal data to redact, for a latency gain.
- **Counting a cloned pass by default.** Rejected by rule 5: the destination never ran the check.
- **Sharing reports.** Deferred: a cloned screening is a "no match" for lists, versions and a matcher the destination never chose, which ADR 0005 allows only beside the search actually made.
- **Carrying an origin chain across hops.** Not built: a copy is refused as a source instead.
- **A third-party scanner action, or a tool installed from a mutable reference.** Rejected after the Trivy compromise of 2026-03-19: a tag can be moved, a pinned digest and a checksummed binary cannot.
- **Copyleft tooling that never ships** (Semgrep's engine, Opengrep, yamllint through `ct lint`, k6). Rejected by rule 4, which allows only MPL-2.0 and EPL-2.0 as unmodified tooling.
- **Claiming conformance with ASVS or MASVS.** Rejected: nobody outside the project has assessed it, so the checklists say "self-assessed" and the wording test keeps it so.
