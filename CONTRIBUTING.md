# Contributing to OpenVerify

Thank you for helping. OpenVerify handles identity documents, faces and personal data, so the bar for correctness, honesty and privacy is high, and this guide is mostly about how we keep it there.

Please read and follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report security issues privately, as [SECURITY.md](SECURITY.md) describes, never in a public issue or pull request.

## Ways to contribute

- **Report a bug** or **suggest a feature** through the [issue forms](https://github.com/hnalpha323/openverify/issues/new/choose).
- **Ask a question** or share an idea in [Discussions](https://github.com/hnalpha323/openverify/discussions).
- **Improve the documentation**: the guides under [`docs/`](docs), the package READMEs, and examples.
- **Review a translation** of the flow's built-in texts ([`docs/i18n/`](docs/i18n/README.md) explains the review status of each catalog).
- **Contribute calibration data or measurements** for a check, made from synthetic or properly licensed data ([`docs/calibration/`](docs/calibration)).
- **Write code**: pick an issue labelled `good first issue` or `help wanted`, or open an issue first for anything larger than a small fix, so the design can be agreed before you invest time.

## Development setup

You need:

| Tool | Version | Used for |
|---|---|---|
| Node.js | 22.18 or later | the TypeScript workspace |
| pnpm | 12 (the version in `package.json`'s `packageManager`; `corepack enable` picks it) | the workspace and its catalog |
| Python and [uv](https://docs.astral.sh/uv/) | Python 3.12 | `services/vision` and the scripts |
| Docker with Compose | recent | local services, integration and end-to-end tests |
| JDK 21 and the Android SDK | Temurin 21 | `android/` only |

```bash
git clone https://github.com/hnalpha323/openverify.git && cd openverify
git config core.hooksPath .githooks       # the secret and PII pre-commit scan (needs gitleaks: infra/scripts/install-gitleaks.sh)
pnpm install --frozen-lockfile
cp .env.example .env                      # replace every change-me-* value
docker compose -f infra/docker-compose.yml --env-file .env up -d --wait   # Postgres, Valkey, RustFS, Mailpit
pnpm --filter @openverify/api db:migrate
pnpm --filter @openverify/api seed:dev    # prints a sandbox API key once
```

[`CLAUDE.md`](CLAUDE.md) is the complete command reference (it is written for coding agents, and it is just as useful for people). [`scripts/env.sh`](scripts/env.sh) shows the environment the maintainers use.

## Running the checks

Run the checks for what you changed before you open a pull request. CI runs all of them.

```bash
pnpm format:check
pnpm lint && pnpm typecheck
pnpm test                       # unit tests; every package gates coverage at 80%
pnpm test:integration           # Testcontainers (Docker)
pnpm e2e                        # the mocked flow suite, then the full-stack Playwright suite (see e2e/README.md)
(cd services/vision && uv run ruff check && uv run ruff format --check && uv run mypy src tools && uv run pytest)
(cd android && ./gradlew testDebugUnitTest testAndroidHostTest koverVerify assembleDebug lint)
pnpm release:check              # the release checklist's machine-checkable rules
```

A single package: `pnpm --filter @openverify/<name> test`. A single test file: `pnpm --filter @openverify/<name> exec vitest run <path> --coverage.enabled=false`.

## The rules

These are the project's non-negotiables. A pull request that breaks one is not merged, however good it is otherwise.

1. **Test first.** Write a failing test, run it and watch it fail for the intended reason, then write the least code that passes, then refactor. Coverage stays at 80% or more per package. For a substantial change, record the evidence (the commands you ran and their output) in `docs/tdd/<slice>.tdd.md`, as the existing files do.
2. **No real personal data, ever.** Test identity documents are synthetic, generated by the fixture scripts; test faces come only from public-domain sources. Never commit, attach or paste a real ID, selfie, name, address or document number, in code, fixtures, issues, logs or screenshots. Logs must not carry OCR text or other PII.
3. **Honest checks.** A heuristic or model-based check ships as `stage: beta` with a confidence score, and its documentation says what it does not detect. A check that needs a licensed data source ships as an adapter plus a deterministic sandbox provider. Never make a check report a pass it did not establish.
4. **Permissive licences only.** Dependencies and model weights must be MIT, Apache-2.0, BSD, ISC, PostgreSQL, CC0, CC-BY, BlueOak-1.0.0, PSF-2.0 or MIT-CMU; [`THIRD_PARTY_LICENSES.md`](THIRD_PARTY_LICENSES.md) records the narrow exceptions. New dependencies are pinned and at least 14 days old. Models and datasets are downloaded by `scripts/fetch-*` with pinned SHA-256 hashes, never committed.
5. **No secrets in git.** Use `.env.example` placeholders. The pre-commit hook and CI scan every change.
6. **Independent naming.** OpenVerify is not affiliated with any commercial identity vendor. Do not use another vendor's name, logo or copied text in the product's UI, branding or documentation (the docs tools enforce this outside `docs/research/` and the plans).

## Conventions

- **Files**: kebab-case file names (Kotlin files use `PascalCase.kt`).
- **TypeScript**: strict mode. zod schemas are the source of truth for API contracts and the OpenAPI spec is generated from them (`pnpm --filter @openverify/api openapi:write`). Errors are RFC 9457 `application/problem+json`. Logging is pino with PII redaction. Fastify routes are registered as plugins.
- **Checks**: IDs are `snake_case` and match the catalog in [`docs/PLAN.md`](docs/PLAN.md) section 4. After changing a check, its defaults or a report, re-render the generated documents: `pnpm --filter @openverify/docs-tools docs:all`.
- **Dependencies**: shared versions live in the pnpm catalog in `pnpm-workspace.yaml`.
- **Database**: migrations are Drizzle migrations in `packages/db`; PII columns use the `encrypted` column helper.
- **Style**: Prettier, ESLint, Ruff and the Kotlin linters decide formatting; do not hand-format against them.

## Commits and pull requests

- Use [Conventional Commits](https://www.conventionalcommits.org): `feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:`, with a scope where it helps (`fix(checks): ...`).
- Sign off every commit to certify the [Developer Certificate of Origin](https://developercertificate.org): `git commit -s`.
- Keep a pull request to one concern. Describe what changed, why, and how you tested it; the [pull request template](.github/PULL_REQUEST_TEMPLATE.md) lists what reviewers look for.
- Add a line under **Unreleased** in [`CHANGELOG.md`](CHANGELOG.md) for any user-visible change.
- Update the documentation in the same pull request as the behaviour it describes.
- Never force-push to `main`. Rebase your own branch freely.
- A maintainer reviews every pull request; CI must be green before merge.

## Documentation assets

- **Illustrations** (`docs/assets/*.svg`) are plain SVG with a light and a dark variant each; the README picks one with `<picture>`. Keep both variants in step.
- **Screenshots** (`docs/assets/screenshots/`) are produced from the end-to-end stack's synthetic data by an opt-in Playwright spec, so they can be regenerated after a UI change instead of being retaken by hand. See the header of [`e2e/tests/docs-screenshots.spec.ts`](e2e/tests/docs-screenshots.spec.ts) for the command. Never take a screenshot of a deployment that holds real data.
