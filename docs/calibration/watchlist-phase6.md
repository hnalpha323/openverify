# Watchlist matching: evaluation and performance (Phase 6, C78.7 and C78.8)

This report measures the name matcher of the watchlist reports (`packages/watchlist`, plan C78) on synthetic data: how often it finds a listed person or company under each kind of name variation, how often its alerts point at the wrong entry, how many alerts it raises on a population of customers who are not listed, and how fast one screening and one re-screen run on synthetic tables in Postgres.

Every number here comes from synthetic data. **Synthetic variation is not real-world variation**: the typos, transliterations, orders and name frequencies below are generated by rules, and real lists, real customers and real data entry differ from them in ways no generator captures. These numbers describe the matcher's behaviour on this set; they are not an accuracy claim about real screening.

The matcher's constants, thresholds, presets and candidate cap were fixed before this evaluation (C78.4, decision 15) and were not changed by it. A number that looks wrong is a finding for the matcher's owner, never a constant change here (H21, V12).

## Method

This section was written and committed before the first evaluation number was measured. A change made afterwards is listed under "Amendments", with its reason.

### Independence (H21, V12)

- **The seed.** The evaluation seed is chosen at run time with a CSPRNG (`openssl rand -hex 16`), after the matcher was committed (its last commit is `f23321b9`, 2026-10-27). It is recorded under "Seed and data" below. Nobody knew the held-out groups before it existed.
- **The measured build.** `packages/watchlist/scripts/build-variant-groups.mjs --hold-out <seed> --output <dir outside git>` filters the pinned variant-group source (`data/manifest.json` entry `rigour_person_names`, SHA-256 `be47a435969da3fa7311d8c682e462d6d20e6cf27cf90ad1473ce213c9a91c79`) and drops, besides the shipped filter, the tenth of the groups that `isHeldOutGroup(id, seed)` selects. The quality measurement uses this build and nothing else.
- **The cases.** fixtures-6's held-out generator (`packages/watchlist/src/testing/held-out/`, imported by path; it is not exported) draws the list, the cases and the customers from the same seed. Its cross-script cases come only from the held-out groups and from its own transliteration rules, not ICAO 9303's tables.
- **The assertion.** Before any screening, the benchmark checks that the build says it is a hold-out build of the pinned source, that every group a case draws on is held out for this seed, and that none of those groups survives in the build. It stops otherwise.
- **Nothing generated is committed.** The list, the cases, the customers, the build and every per-query result stay in a directory outside git (`/tmp/openverify-eval-6/`). Only aggregates are published here. A group case combines two real name forms, so it may spell a name some real person bears; that is why the set exists only at run time.
- **No tuning.** The evaluation never changes a constant, a threshold, a preset, the candidate cap or matcher code.

### The held-out set

Generated by `generateHeldOutSet({ seed, persons: 2000, companies: 600, customers: 10000, groups: <every group of the pinned source>, groupCases: 500 })`.

- **Listed persons** (2,000). Fictional names built from authored syllables. A tenth are listed in Cyrillic only. Each has one case, whose query varies the name by one source, in turn: `exact`, `typo` (one letter substituted, inserted, deleted or two transposed, in the family name), `order_swap`, `dropped_middle`, `initials` (the given name as an initial), `joined_tokens` (middle and family names written as one word), `split_tokens` (the family name split in two), `own_transliteration`. The last has two forms: a Latin-listed person queried in Cyrillic by the generator's own phonetic rules, and a Cyrillic-listed person queried in Latin by its own German-style or French-style romanisation. Both are reported together, and also apart.
- **Listed companies** (600). Fictional names with a legal form. Cases: `exact`, `typo` (in the first word), `legal_form` (the legal form written another way, or left out).
- **Held-out group persons** (500 for each of the two sources). Each listed person's given and family names are two Latin forms of two held-out groups. `held_out_group_cross_script` queries them in another script of the same groups; `held_out_group_same_script` queries them in another Latin spelling of the same groups.
- **Customers** (10,000). Synthetic persons, never listed: each name token is drawn half from fictional syllables and half from the Latin forms of every group of the pinned source, combined at random, with a birth date from 1940 to 2005 and, for half of them, a country.
- **The list** holds every listed entry, about 3,600, in one source.
- **Two query variants for person cases:** names only (the generator's default; it measures name matching) and with the listed birth date (the default configuration's date qualifiers at work). Customers always carry a birth date.

### How each query is screened

Through the production code path, end to end:

1. A Postgres started by Testcontainers (`pgvector/pgvector:pg17`, with the C73.8 flags of `POSTGRES_TEST_COMMAND`), migrated with the repository's migrations.
2. The list is imported by `syncWatchlistSource` into the synthetic sandbox source `openverify-sandbox`, keyed with the held-out build. The import format is the normalised JSON.
3. Each query runs the report job's screening (`screenNames` in `apps/api/src/jobs/reports/screening.ts`): the `watchlist` job for persons and customers, the `business-watchlist` job for companies. That is the source's state, candidate retrieval (rare keys, trigrams, identifiers; at most 2,000 candidates), the entry loads, scoring, the presets' minimums and coverage, for a sandbox environment.
4. The configuration is the type's default (`REPORT_CONFIG_DEFAULTS`), with `name-matching` set in turn to each fixed preset: `exact`, `strict` (minimum 0.85) and `tolerant` (minimum 0.80). The defaults are `tolerant` for `watchlist` and `strict` for `business-watchlist`. `custom` has no fixed constants and is not measured.
5. A query's matches are the matches the job keeps (at or above the preset's minimum, or by the identifier or weak-alias rule). Retrieval does not depend on the preset, so each query's database reads are made once and reused for the three presets.

### Metrics

Computed per preset, per subject kind (persons, companies) and, for person cases, per query variant:

- **Recall per variant source:** the cases whose expected entry is among the matches, over the cases of that source.
- **Precision:** the matches to the expected entry, over all matches of the case queries.
- **Alerts per 1,000 customers:** 1,000 times the customers with at least one match, over all customers. Customers are not listed, so every customer alert is a false alert, although a random combination can equal a listed name.

The counts behind each value are published with it.

**Diagnostics** are reported with the metrics but are not metrics:
- misses whose run stated an incomplete coverage (`coverage.limits`, for example `lossy_script`);
- runs whose search was cut at the candidate cap, and runs that ended `errored`;
- the group cases whose listed and query forms share a group that survives in the measured build. Another group can hold both forms, which is legitimate knowledge, so these cases are counted, not removed.

### Intervals

Each metric has a 95% interval from 2,000 bootstrap replicates **over listed identities, not over pairs**.

- Each replicate draws the listed entries with replacement, as many as the list holds. The list of a replicate is the set of entries drawn.
- A case counts once per draw of its entry.
- A match to another entry counts as a false match only when that entry was drawn.
- For the alert rate, the replicate also draws the customers with replacement. A customer alerts when one of its matches was drawn.
- The interval is the 2.5th to 97.5th percentile of the replicates (nearest rank).
- The same draws serve every preset and variant, so the presets are compared on paired samples. The bootstrap stream is seeded from the evaluation seed.

### Performance (C78.7)

- **The machine** is stated with every run: CPU model, cores, memory, OS, Docker, the Postgres image and Node.
- **The tables** are synthetic, generated at run time by `packages/watchlist/scripts/benchmark-tables.mjs` from a seed derived from the evaluation seed.
  - Names are drawn by a Zipf law (exponent 1, ranks shuffled by the seed) over a pool of fictional syllable names and the Latin forms of the variant groups. They are combined at random, so no entry is a real person. Real name frequencies are heavy-headed, and a flat draw would make every name rare.
  - Aliases use Cyrillic and Arabic renderings of the fictional names and the other-script forms of the groups.
  - Two profiles:
    - sanctions-like, about 1.65 names per entry, at **100,000** list names;
    - PEP-like, about 5 names per entry in several scripts, at **2,000,000**.
- **The import** goes through `syncWatchlistSource` into the sandbox source, so `analyzeWatchlistTables` and the key-frequency rebuild run as for an operator (owner decision 10). The benchmark passes a copy of the manifest whose byte caps for that source are raised: the committed cap is 16 MiB, and the normalised file at 2,000,000 names is several hundred megabytes.
  - At 100,000 names the import is one sync.
  - At 2,000,000 the import is successive syncs, each a full publication that grows by 250,000 names. A single sync of 2,000,000 names does not fit one 10-minute call.
  - Before measuring, the list tables get a `VACUUM ANALYZE`: the state after autovacuum.
- **One screening** is the `watchlist` job's screening as above, with the default configuration (`tolerant`), the shipped variant groups (`data/variant-groups.json`) and a sandbox environment.
- **Subjects** (300):
  - 150 listed entries' primary names, with their birth dates;
  - 150 unlisted names drawn from the same Zipf law, with random birth dates.

  There are 20 warm-up screenings, then three rounds over the 300.
- **Timings:**
  - The headline p95 is the nearest-rank p95 over all 900 timings.
  - Also reported: p50, p99, each round's p95 (the C78.7 gate in `apps/api` reads the least disturbed round), and the phases (source state, retrieval, entry loads, and the rest: scoring and coverage).
  - The load average of the machine is read before and after.
- **How often the cap binds:** the share of the 300 subjects (first round) whose retrieval reached the 2,000-candidate cap, with a 95% Wilson interval. Also the share that would end `result_truncated`: cut short, with no match kept.
- **Budgets:** 100 ms at 100,000 names and 250 ms at 2,000,000 (C78.7).
- **The re-screen.**
  - The setting: the 100,000-name database, with 200,000 recurring `watchlist` reports in one sandbox environment, pinned to the source. Their queries are drawn from the unlisted law, with birth dates.
  - The changes: three syncs, adding 100, 1,000 and 10,000 entries drawn from the list's law (amended to 100, 300, 1,000 and 3,000: see "Amendments", 1).
  - The timing: after each sync, `processReportRescreen` (`apps/api/src/jobs/reports/rescreen.ts`) is timed end to end. The runs it inserts are reported.
  - The budget is 60 s per environment per sync (C74.4).
- **A number over budget is a finding** for `api-watchlists` or the owner, never a constant change.

### What this set does not cover

- Real names, real lists and real data entry. The variations are rules applied to fictional names and to name forms combined at random.
- Name frequencies: the performance tables assume a Zipf law; real lists and real customer bases have their own.
- Scripts beyond the generator's: cross-script cases use the held-out groups' scripts and Cyrillic. Han, Thai and other scripts are compared only through lossy forms, which coverage flags.
- PEP positions, classes and relatives, adverse media, identifiers, vessels, aircraft and crypto addresses.
- Weak aliases (off by default) and the `custom` preset.
- Business customers: the customer population is persons only, so companies have recall and precision but no alert rate.
- Lists of other sizes: the quality list holds about 3,600 entries. The alert rate grows with the list's size.

## Amendments

Made before the evaluation seed existed, so before the first evaluation number.

1. **Re-screen sizes.** The method named syncs adding 100, 1,000 and 10,000 entries. A development run on a scratch seed (not the evaluation seed) took 130 s to re-screen 1,000 added entries against 200,000 subjects. At that rate, 10,000 entries take about 19 minutes, more than one 10-minute call. The sizes are therefore 100, 300, 1,000 and 3,000, each one call.
2. **Development runs.** The plumbing was checked on that scratch seed:
   - quality: a small set (40 persons, 12 companies, 60 customers, 10 group cases per source);
   - performance: the 100,000-name import and measurement, the re-screen seeding and its 100- and 1,000-entry syncs, the first two 2,000,000-name syncs;
   - a parse of a full 2,000,000-name file in the sync's 12 GiB heap.

   None of those numbers is reported here. Every number below comes from the evaluation seed, from an empty output directory.
3. **Rendering.** The tables below are printed from the result files by `packages/watchlist/scripts/benchmark-render.mjs` (the renderer is tested), not copied by hand.

**What the numbers say.**
- **Each fixed preset finds what its rules allow.**
  - `exact` finds the same name in any order. It also finds 33.0% of the Latin-listed persons queried in the generator's own Cyrillic, whose rendering transliterates back to the same Latin name.
  - `strict` adds dropped middle names, initials, joined and split tokens and legal forms, each at 100%.
  - `tolerant` adds one typo per token of at least 5 characters: 71.0% of person typos and 56.5% of company typos.
- **Cross-script recall without the variant group is low.** A held-out group case is a name whose group the measured build does not know.
  - `tolerant` finds 14.6% (11.7–17.8%) of the cross-script cases and 26.8% (22.9–30.7%) of the same-script spellings.
  - `strict` finds 4.2% and 2.6%.
  - Only 2 of the 500 cross-script cases have both name parts linked by another group that survives in the build; 103 have one.

  So the matcher's cross-script reach comes from its groups. A name outside them is found only when its transliteration happens to agree.
- **The generator's own romanisations of Cyrillic.** `tolerant` finds 50.5% of the Cyrillic-listed persons queried in German- or French-style Latin, and 62.5% of the Latin-listed persons queried in the generator's Cyrillic.
- **A birth date changes little.** Under `strict`, the exact date's +0.05 lifts the cross-script cases from 4.2% to 6.8%. `tolerant` is unchanged (73 of 500).
- **This set cannot measure false alerts.**
  - Precision is 100% at every preset: no case matched another entry.
  - No customer alerted at any preset: 0 of 10,000. The bootstrap interval is degenerate at zero events; the 95% Wilson upper bound is 0.38 per 1,000.
  - The reason is the list: it holds 2,600 fictional names and 1,000 pairs of held-out forms. A customer would have to repeat both names of one entry, and a random birth date then lowers the score.
  - The post-hoc observation under "Performance" shows what common names do.
- **Most misses read as complete.** Under `tolerant`, 416 of the 1,025 missed person cases ran with an incomplete coverage (`lossy_script`), so their report says the answer is weaker. The other 609 misses read as complete. Coverage describes how the scripts were compared, not spelling variation. A complete-coverage miss is one of:
  - a typo past the budget;
  - a romanisation of Cyrillic that ICAO's does not give (ICAO transliteration counts as complete);
  - an unknown Latin spelling.
- **No search was cut at the cap, and no run errored,** on this 3,600-entry list.

**Post-hoc breakdown of the typo cases.** This breakdown is not in the method; it comes from the same observations.

## Findings

Each is for its owner. None was acted on here: the evaluation changes no constant, rule or code (H21).

1. **Adjacent transpositions are never typos** (`watchlist-matcher`; a rule change needs a calibration report, decision 15). The typo rule's Levenshtein distance of 1 misses all 98 transposition cases, while it finds 98% of the other single-letter typos. These are post-hoc counts from run 1 that no committed step reproduces (see "Post-hoc breakdown of the typo cases"). An optimal-string-alignment (Damerau) distance of 1 would take them in. Its effect on false matches would need measuring on a set that can measure them (finding 5).
2. **Misses outside the variant groups are mostly silent** (`watchlist-matcher`, the owner).
   - Coverage flags lossy scripts.
   - A Cyrillic romanisation that ICAO's table does not give, and an unknown Latin spelling, are misses with complete coverage: 609 of `tolerant`'s 1,025 person misses.
   - Whether `transliterated` should be a coverage limit, or the docs should say what complete coverage does not promise, is the owner's call. `docs/reports/watchlist.md` explains `lossy_script` only.
3. **Screening misses its budget at both scales on heavy-headed names** (`api-watchlists`; owner decision 11's carried items).
   - The p95 is 290.8 ms at 100,000 names and 2,309 ms at 2,000,000 (1,444 ms compacted, a post-hoc round of run 1 only).
   - The 2% document-frequency share lets a single key return more than the cap at PEP scale, so the cap binds in about half the searches and 7% end `result_truncated`.
   - One retrieval took 49.4 s.
   - Folding the rare-key lookup into the candidate query (decision 11) addresses retrieval time. A frequency limit that does not grow with the source (for example, no key held by more names than the cap) would address the truncation. Both are owner decisions with a calibration report.
4. **The re-screen misses its 60 s budget from about 1,000 changed entries** at 200,000 subjects (99.2 s at 1,000; 288.1 s at 3,000), and its permissive forward screen inserts 8 to 54 runs per added entry on common names, each a full screening later (`api-watchlists`).
5. **The held-out set cannot measure false alerts** (`fixtures-6`, the owner).
   - It gives 100% precision and 0 alerts at every preset, because its list is sparse in name space.
   - A list drawn from a heavy-headed law over real name forms (as the performance tables are) would measure them.
   - The post-hoc 24.7% of unlisted names alerting at 100,000 names (run 1 only, not reproduced by committed code) suggests real alert rates are much higher than this set shows.
6. **The C78.7 gate measures an easy case** (`api-watchlists`). It uses fictional names with rare tokens and empty variant groups, so it passes (85.7 ms) while a heavy-headed law with the shipped groups gives 290.8 ms on the same machine.
