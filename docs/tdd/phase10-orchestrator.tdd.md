# Phase 10: the orchestrator's slices between Workflows

## Dependency verification on a cold Gradle home (after Workflow 10A, 2026-11-09)

The 10A push (`7d985a77`, CI run 42603210118) failed the `android` job in 37 s, at configuration, before any task ran:

```
* What went wrong:
A problem occurred configuring root project 'openverify-android'.
> Dependency verification failed for configuration 'classpath'
  4 artifacts failed verification:
    - guava-parent-33.4.0-jre.pom (com.google.guava:guava-parent:33.4.0-jre) from repository MavenRepo
    - junit-bom-5.10.2.module (org.junit:junit-bom:5.10.2) from repository MavenRepo
    - junit-bom-5.11.0-M2.module (org.junit:junit-bom:5.11.0-M2) from repository MavenRepo
    - kotlinx-coroutines-bom-1.8.0.pom (org.jetbrains.kotlinx:kotlinx-coroutines-bom:1.8.0) from repository MavenRepo
```

`android-instrumented` was skipped behind it. Locally every Android gate call had passed, including the orchestrator's full validation
(`validate-full.sh`, 24 of 24 rows) and a `--rerun-tasks` run of the screenshot step.

**Cause.** Dependency verification is new in 10A (C214.5, decision 67; `ec973b08`, `a1b1eab6`). foundation-10a wrote
`android/gradle/verification-metadata.xml` in a scratch worktree, but with the shared, warm `~/.gradle`
(`docs/tdd/phase10-foundation-10a.tdd.md`, checkpoint 4). A cold home, as on a CI runner, downloads more metadata for the build script's
plugin classpath: the Gradle module files of two JUnit BOMs where the warm cache had read only their POMs, and parent and BOM POMs the warm
cache never asked for. The metadata never held them, so a cold build fails before configuration ends.

**RED** (local, no code change): the CI failure reproduced with a fresh `GRADLE_USER_HOME`:

```
$ GRADLE_USER_HOME=<scratch>/gh-cold-red ./gradlew --no-daemon help
rc=1 (40 s), the same four artifacts, "Dependency verification failed for configuration 'classpath'"
```

**GREEN.** The metadata written from a cold home, then proved in a second cold home with verification on. The plan's recipe (Stage 1b
amendment 14) with a fresh `GRADLE_USER_HOME`:

1. `--write-verification-metadata sha256` over every call of CI's `android` job and the device-test compile: `help testDebugUnitTest
   testAndroidHostTest koverVerify assembleDebug :openverify-sdk:assemble lint :openverify-sdk:screenshotTest -Proborazzi.test.verify=true
   checkKotlinAbi :demo-app:bundleRelease assembleAndroidDeviceTest :demo-app:assembleAndroidTest checkDependencyBoundary`: rc=0, 195 s.
2. The full graph, as foundation-10a's second pass: `--write-verification-metadata sha256 --continue resolveAndLockAll --write-locks
   connectedAndroidDeviceTest`: rc=1 by design ("No connected devices!"), 82 s. The lockfiles are unchanged (`git status` shows only the
   metadata).
3. Added: 12 artifacts in 33 lines, every one a SHA-256 "Generated by Gradle" from Maven Central, nothing removed: the four above, and
   `guava-parent-33.6.0-jre.pom`, `groovy-bom-4.0.29.pom`, `bc-jdk18on-bom-1.85.pom`, `junit-bom-5.13.3.pom`, `junit-bom-5.14.4.pom`, with
   their components. Signatures stay unverified and metadata verification stays on, as decision 67 says; no lenient mode, no
   `--dependency-verification` flag.
4. Proof in a second fresh home (`<scratch>/gh-cold-verify`), verification on, CI's exact commands:
   - `testDebugUnitTest testAndroidHostTest koverVerify assembleDebug :openverify-sdk:assemble lint --stacktrace`: rc=0, 352 s (1,934
     host tests, 0 failures);
   - `:openverify-sdk:screenshotTest -Proborazzi.test.verify=true checkKotlinAbi :demo-app:bundleRelease --stacktrace`: rc=0, 90 s;
   - `assembleAndroidDeviceTest :demo-app:assembleAndroidTest`: rc=0, 66 s.

**Guard.** The orchestrator's `validate-full.sh` now runs its two Android rows with a fresh `GRADLE_USER_HOME`, so a metadata gap fails the
local validation before a push. Whoever changes a dependency writes the metadata from a fresh `GRADLE_USER_HOME` (the recipe above). The
runner's own proof (the `android` job, then the screenshot comparison on the GitHub runner and the emulator job) comes with the 10B push:
10B's known item KP10-4.

## The consumer-rules check reads an AAR no CI step built (after Workflow 10C, 2026-11-10)

The 10C push (`67244eb78`, CI run 42937477615) failed the `android` job at "The consumer rules as R8 applied them":

```
AAR: openverify-sdk.aar ships 2 consumer rule(s), as committed
release: R8 read the SDK's rules from the library and kept every serialization exception's name
FAIL: /home/runner/work/openverify/openverify/android/openverify-nfc/build/outputs/aar/openverify-nfc-release.aar is missing: run ./gradlew :openverify-sdk:assemble assembleDebug
check-consumer-rules: failed
```

Cause: `check-consumer-rules.py` reads `openverify-nfc-release.aar`, and neither `ci.yml`'s android job nor `android-release.yml`'s gate builds it (`assembleDebug` builds the debug AAR; the demo's release build does not bundle the library's AAR). The local validation of 10C passed because the build directory still held a release AAR from earlier work. (The same run's `unit-api-coverage` job did not start: GitHub reported the account's spending limit. `android-instrumented` was skipped because `android` failed.)

RED (`6c2ffc9af`), `bash infra/tests/ci-workflow.test.sh`:

```
FAIL - android: the release build step also builds openverify-nfc's release AAR, which the consumer-rules check reads
FAIL - release: gate: openverify-nfc's release AAR is built before the consumer-rules check reads it
# 368 passed, 2 failed, 0 skipped
```

GREEN: both workflows add `:openverify-nfc:assembleRelease` to the release build step, and the script's hint names the tasks that build what it reads. `# 370 passed, 0 failed, 0 skipped`.

The CI failure reproduced and fixed locally, with the stale AAR moved out of the build directory:

```
$ python3 -I scripts/check-consumer-rules.py
FAIL: .../android/openverify-nfc/build/outputs/aar/openverify-nfc-release.aar is missing: run ./gradlew :openverify-sdk:assemble :openverify-nfc:assembleRelease
check-consumer-rules: failed            (rc=1)
$ ./gradlew --no-daemon -q :openverify-nfc:assembleRelease      (rc=0)
$ python3 -I scripts/check-consumer-rules.py
AAR: openverify-sdk.aar ships 2 consumer rule(s), as committed
AAR: openverify-nfc-release.aar ships 0 consumer rule(s), as committed
release: R8 read the SDK's rules from the library and kept every serialization exception's name
minifiedSmoke: R8 read the SDK's rules from the library and kept every serialization exception's name
check-consumer-rules: passed (R8's outputs only; the minified app was not run)   (rc=0)
$ python3 -I -m unittest discover -s scripts/tests

```

Not pushed alone (one push per Workflow): it rides with 10D's push. The orchestrator's `validate-full.sh` now runs `clean` before its first Android row, so a stale build output cannot hide a missing step again; 10D's integration agent runs the android job's steps once from a clean build directory.
